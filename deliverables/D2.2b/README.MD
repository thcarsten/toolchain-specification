# D2.2b: extension of data space reference architectures with Generic Toolchain Architecture

Deliverable D2.2a introduced the Generic Toolchain Architecture, realised in this repository as the toolchain specification and its pipeline generator: a semantic pipeline description in the *toolchain* ontology (`tcs:`), validated against a SHACL application profile and compiled by the pipeline generator into deployable artefacts. This deliverable applies the pipeline generator to two existing Linked Data reference architectures of the City of Bruges, both built independently of DiSHACLed. They were selected because their components already exchange RDF, which makes SHACL-based validation of component interfaces meaningful and turns them into a realistic test of whether the toolchain specification can describe and regenerate hand-built pipelines.

For each architecture, the diagram shows the original stack and the stack under DiSHACLed, in which a single pipeline definition generates the processing components (dashed boxes) while infrastructure without a catalog type, such as LDES servers, proxies and frontends, remains hand-written (solid boxes).

**Brugge fietsstallingen** (bicycle parking). The original consists of three hand-written Docker Compose projects around LDIO: a publisher that maps GeoJSON to OSLO and writes to an LDES server, a consumer that follows the LDES into Virtuoso, and Trifid subject pages. Under DiSHACLed, [pipeline_definition_fietsstallingen.revised.ttl](../../pipeline%20generator/data/pipelines/pipeline_definition_fietsstallingen.revised.ttl) declares two plans. The publisher is a one-to-one LDIO re-expression; the consumer is a cross-framework pipeline in which LDIO forwards LDES members to RDF-Connect for skolemisation and SPARQL ingestion into a generated triple store. The comparison of generated and original artefacts is recorded in [GENERATOR-GAPS.md](../../GENERATOR-GAPS.md).

![Brugge fietsstallingen](images/fietsnieten_dishacled_architecture.png)

**Brugge waterkwaliteit** (water quality). The original is a NiFi process group on the UrbanSense platform, drawn by hand: monthly blobs are fetched from Azure Blob Storage, split, mapped to OSLO JSON-LD by a Groovy script, wrapped as version objects and posted to an LDES server. Credentials, canvas wiring and the LDI extension install were all manual. This case introduced Apache NiFi 2 as a fourth target framework. From [pipeline_definition_nifi.ttl](../../pipeline%20generator/data/pipelines/pipeline_definition_nifi.ttl) the generator emits the persisted flow, a Dockerfile with the LDI bundle, and a Compose file; secrets are referenced by name and bound at deployment time, and a remote mode uploads the flow to the existing Urban Sense platform's Nifi instance instead of building a local image.

![Brugge waterkwaliteit](images/waterkwaliteit_dishacled_architecture.png)

Across both cases, every processing component could be described and regenerated, and the boundary between generated processing and hand-written infrastructure proved stable. Open items (compose `depends_on` ordering, one plan per generator run, LDIO service definition in the catalog) are tracked in [ROADMAP.md](../../ROADMAP.md). Diagram sources: [fietsnieten_dishacled_architecture.drawio](fietsnieten_dishacled_architecture.drawio), [waterkwaliteit_dishacled_architecture.drawio](waterkwaliteit_dishacled_architecture.drawio).
